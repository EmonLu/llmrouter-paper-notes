> 用一句话说明：这篇论文解决了什么问题、用了什么方法、取得了什么结果。

- 总结：论文把 multi-turn reasoning 形式化为一个带全局 token 约束的 sequential compute allocation 问题，提出用 GRPO 训练的 TAB（Turn-Adaptive Budgets）在每一轮根据历史上下文动态分配 token budget，在数学推理 benchmark 上实现最高可达 35% 的 token 节省，并保持或提升准确率；若已知全部未来子问题，TAB All-SubQ 最多可达 40% 节省。

## 3. 研究问题
> 这一部分回答“为什么要做这件事”。

### 3.1 核心问题是什么？
- 现有高效推理方法大多把预算分配当成 single-turn / one-shot 问题，对整道题只分配一次推理预算。
- 但在 multi-turn reasoning / sub-question decomposition 中，不同 turn 的难度差异很大：有的 turn 只是 bookkeeping，有的 turn 决定最终成败。
- 核心问题是：如何在一个完整多轮轨迹里，把有限的总 token 预算更合理地分配到不同 turn，而不是每一轮都一刀切？

### 3.2 为什么这个问题在大模型路由场景中重要？
- 这其实是“预算路由（budget routing）”问题：不是选哪个模型，而是选每一步该给多少 compute。
- 多轮推理里，前面生成的长回答会进入后续上下文，导致长上下文成本持续累积；一旦早期 turn 浪费 token，后面关键步骤就会被“预算挤压”。
- 在 agent / decomposition 系统里，这类 sequential budget allocation 比单次 query routing 更贴近真实部署场景。

### 3.3 该问题主要对应哪些目标？
> 可多选：质量、成本、延迟、可扩展性、鲁棒性、可解释性、在线适应性、部署效率等。

- 目标类型：质量、成本、推理效率、长上下文开销控制、部署效率
- 我的理解：TAB 的本质不是缩短所有响应，而是“把预算留给真正关键的 turn”，因此它优化的是 trajectory-level 的 accuracy-token trade-off。

## 4. 方法概览
> 这一部分回答“它是怎么做的”。

### 4.1 论文提出的方法是什么？
- 提出 TAB: Turn-Adaptive Budgets。
- 将 multi-turn reasoning 建模为 scalarized multi-objective MDP：状态是当前 conversation trajectory 加当前 sub-question，动作是本轮选择的 token budget，最终奖励同时考虑任务正确性和是否超过全局预算。
- 预算器（Budgeter）使用 GRPO 训练，学习在每个 turn 给 solver 分配离散预算。
- 对于预先已知完整子问题计划的系统，还提出 TAB All-SubQ，让预算器在分配当前 turn 预算时同时看到过去与未来所有 sub-questions。

### 4.2 Router 的输入是什么？
> 例如：query、历史对话、用户画像、候选模型特征、预算、延迟约束、环境状态等。

- 输入：
  - 当前 turn 之前的 conversation trajectory `x1:t-1`
  - 当前 sub-question `qt`
  - TAB All-SubQ 额外可访问全部子问题序列 `{q1, ..., qT}`
  - 隐含的全局每题 token budget 约束

### 4.3 Router 的输出是什么？
> 例如：选择哪个模型、是否 fallback、是否 cascade、是否继续推理、分配多少预算等。

- 输出：
  - 当前 turn 的 token budget `bt`
  - 预算取自离散集合 `B = {256, 512, 1024, 2048, 4096}`

### 4.4 Routing 决策是如何产生的？
> 例如：规则、分类器、打分器、排序器、policy、bandit、gating network 等。

- 决策机制：
  - 预算器是一个 policy model `πϕ`
  - 通过 RL（GRPO）在轨迹级奖励下学习 budget allocation
  - 奖励是“最终正确性 - 超预算惩罚”的标量化目标
  - 本质上是 sequential budget policy，而不是基于启发式阈值的预算规则

### 4.5 是否需要训练 Router？
- 是否训练：`是`
- 如果需要，训练数据是什么：MATH 训练集中的 Level-5 问题，被一个“User LLM”分解成多轮子问题轨迹，再由 solver 与 budgeter 交互形成训练轨迹。
- 训练目标是什么：最大化最终任务正确率，同时通过预算惩罚项约束全局 token 消耗。

### 4.6 涉及哪些学习机制？
> 可多选：强化学习、监督学习、蒸馏、bandit、ranking、classification、gating、heuristic 等。

- 学习机制：强化学习（GRPO）、LoRA finetuning、多目标优化
- 我的理解：这篇论文把预算控制从“rule-based difficulty estimate”提升成了 trajectory-level policy learning。

## 5. 系统架构
> 这一部分回答“它在系统里怎么接入”。

### 5.1 整体 Pipeline 是怎样的？
- 一个多轮数学推理系统包含三个角色：
  1. User LLM：把原始数学题分解为若干 sub-questions
  2. Budgeter：在每轮根据历史与当前问题分配 token budget
  3. Solver：在给定 budget 下生成当前 turn 响应
- 整体按子问题顺序推进，最后依赖整个 trajectory 的结果判断正确性并回传 RL 奖励。

### 5.2 包含哪些模型 / 模块？
- User：Qwen3-8B
- Budgeter：Qwen3-1.7B（经 RL + LoRA 微调）
- Solver：L1-Qwen3-8B-Exact
- 环境中关键模块：
  - 子问题分解器
  - 预算分配器
  - 受 budget 约束的 solver
  - 终局 reward / verifier

### 5.3 路由发生在哪个阶段？
> 例如：请求进入前、生成前、生成中、agent planning 阶段、tool 调用前后等。

- 路由阶段：每个 turn 生成前，Budgeter 先决定本轮允许的 reasoning token budget，再由 Solver 生成。

### 5.4 是否支持以下能力？
- 动态 fallback：`否（不是模型切换意义上的 fallback）`
- cascade：`否（重点是预算分配而非多模型级联）`
- multi-step decision：`是`
- online update：`否，论文中主要是离线训练后的推理`

### 5.5 我对系统架构的理解
- 这是一个“预算控制器 + 固定 solver”的系统，与传统 router 最大不同是：控制对象不是“模型 ID”，而是“每一步推理深度”。
- 如果把多模型 routing 与本文结合，可以进一步扩展为 joint model-budget routing：先决定本步用哪个 solver，再决定给多少 token。

- 主实验使用 5 个数学推理测试集：
  - MATH-500
  - AMC23
  - MATH Level-5
  - OlympiadBench
  - AIME25
- 训练时使用 MATH 训练集中的 Level-5 问题。
- 额外 OOD 更难测试集：
  - TheoremQA
  - BBEH-Mini
  - GPQA-Main
- appendix 表格把每个主实验 benchmark 的详细准确率 / 总 token 都列全了；OOD 三个集合同样给出完整数值，因此论文不仅有宏平均，还能回看到单数据集 trade-off。

### 6.2 对比了哪些 Baseline？
- Static：每个 turn 固定同一预算，预算来自同一离散集合。
- LLM-Judge Individual：只看当前子问题 `qt`，由一个 off-the-shelf LLM 直接判断本轮预算。
- LLM-Judge Multi-Turn：看历史 trajectory 与当前子问题后，由 off-the-shelf LLM 分配预算。
- TAB All-SubQ 还与“知道全部子问题但非 RL 学得的 LLM-Judge Multi-Turn All-SubQ”进行比较。

### 6.3 评估了哪些任务类型？
> 例如：chat、QA、math、code、tool-use、agent tasks、benchmark routing tasks 等。

- 多轮数学推理
- 通过子问题分解进行 sequential reasoning 的任务
- 更难的 theorem-level / scientific reasoning OOD 任务

### 6.4 使用了哪些大模型或专家模型？
- User：Qwen3-8B
- Budgeter：Qwen3-1.7B
- Solver：L1-Qwen3-8B-Exact
- 另有更强预算器实验：Qwen3-4B Budgeter（图 5 提到比 1.7B 更强）
- appendix / prompts 还明确：Budgeter 输入是 conversation trajectory + 当前子问题；TAB All-SubQ 额外看到全部子问题；Solver 每轮响应上限 4k token，最大 context 32k。

### 6.5 主要评估指标是什么？
> 例如：accuracy、win rate、cost、latency、token usage、throughput、success rate 等。

- Accuracy
- Total tokens used（论文特别强调统计 User + Budgeter + Solver tokens）
- Accuracy-token trade-off / Pareto 风格比较

## 7. 核心结果
> 这一部分只记录最关键结果，不要机械抄整张表。

### 7.1 最重要的实验结果是什么？
- TAB 在 5 个数学 benchmark 上都表现出更优 accuracy-token trade-off，最高可比 baseline 节省 35% token，同时维持或提升准确率。
- 宏平均（Macro Average）上，TAB with `B = 5k` 可在 58.5% accuracy 下优于 LLM-Judge Multi-Turn 的 token 使用。
- TAB with `B = 8k` 相比 baseline 达到 4.4 个百分点更高准确率，同时还节省 8.5% 总 token。
- TAB All-SubQ with `B = 10k` 在无损准确率的情况下，相比标准 TAB 再节省 12% token，相比 baseline 最多节省 40%。
- 在 OOD 更难数据（TheoremQA、BBEH-Mini、GPQA-Main）上，TAB 依然保持更好的 accuracy-token trade-off。
- appendix 数值里几个更有代表性的单集结果：
  - MATH-500：TAB `B=10k` 达到 86.6 / 6350 tok，优于 Static-4096 的 85.8 / 10468 tok。
  - AMC23：TAB `B=8k` 达到 77.5 / 5587 tok，明显优于 LLM-Judge Multi-Turn 的 70.0 / 5923 tok。
  - OOD 的 TheoremQA：TAB `B=10k` 为 42.3 / 6566 tok，高于 Static-4096 的 42.1 / 10754 tok。

### 7.2 相比 Baseline 提升了什么？
- 相比 Static：避免对简单 turn 过度思考。
- 相比 LLM-Judge Individual：不再把预算决策当作“独立 turn 的局部难度预测”，而是考虑历史依赖。
- 相比 LLM-Judge Multi-Turn：TAB 学到了更稳定的 sequential allocation policy，不会像 judge baseline 那样过多集中在高预算（文中提到 LLM-Judge 倾向于围绕 2048 token 高计算值聚集）。

### 7.3 是否在质量、成本、延迟之间取得了更好的 trade-off？
- 是，主要体现在质量-成本（accuracy-token）权衡上。
- 论文虽然没有系统报告端到端 latency，但从动机与指标看，减少无效 token 也会间接减少长上下文和推理时延开销。
- 这篇论文的核心贡献就是把“更省 token”与“保持正确率”统一起来，而不是单纯压缩输出长度。

### 7.4 有哪些 Ablation Study 或 Sensitivity Analysis？
- 不同全局预算 `B ∈ {3k, 5k, 8k, 10k}` 的比较：预算越大，TAB 相对 baseline 的节省优势通常越明显；在很低预算（如 3k）下，由于预算桶过少，自适应空间受限。
- TAB All-SubQ：验证“知道未来子问题”确实能进一步优化预算分配。
- 更强预算器（Qwen3-4B）优于 Qwen3-1.7B，说明 budgeter 能力会影响最终 trade-off。
- 预算分配直方图分析：TAB 更符合“简单 turn 少给、难 turn 多给”的预期行为。
- appendix qualitative examples 很有价值：
  - B.1：TAB 用 2605 token 解对一道题，而 LLM-Judge Multi-Turn 用 6063 token 才完成，体现它会给简单子问题只分配 256 token。
  - B.2：Static-512 在关键早期步骤被硬截断，整题 3198 token 仍答错；TAB 把关键步提到 1024 token，整题 3548 token 反而答对，说明它不是盲目省 token，而是在关键步加码。
- prompts appendix 也验证了系统接口是清楚的：Solver turn prompt 明确要求 “Think for exactly budget tokens”，最终 synthesis 统一输出 boxed answer。

## 8. 贡献与创新点
> 这一部分用于提炼“这篇论文为什么值得记”。

### 8.1 主要贡献是什么？
- 首先把 multi-turn reasoning 的 compute allocation 明确建模为 sequential decision / multi-objective MDP。
- 提出 RL 学习的 TAB 预算器，而非 heuristic 或单次 judge。
- 证明“多轮预算分配本质上是 planning 问题”，而不只是局部 difficulty estimation。
- 提出 TAB All-SubQ 进一步说明：未来子问题信息对预算分配很重要。

### 8.2 相比已有方法的新意在哪里？
- 现有 adaptive compute / budget methods 多数停留在 single-turn；本文把问题推进到 trajectory-level。
- 相比 model routing，这种方法不需要多模型切换的基础设施成本，也避免 cross-model transition 的 prefill/decode 开销。
- 相比“让 LLM judge 当前问题难度”，TAB 使用 RL 从最终结果反向学习预算策略，能处理 delayed feedback 和 credit assignment。

### 8.3 创新类型属于哪一类？
> 可多选：新的 routing 策略、新的训练目标、新的数据构造方式、新的系统架构、新的 benchmark 等。

- 创新类型：新的 budget routing 策略、新的 sequential MDP 形式化、新的 RL 训练目标
- 我的判断：这篇论文更像是在“adaptive compute routing”方向上补上 multi-turn 这一关键缺口。

## 9. 局限性
> 这一部分非常重要，用来防止“只看到优点”。

### 9.1 方法有哪些假设？
- 假设任务可以被分解成多轮子问题序列。
- 假设 solver 支持相对稳定地遵守指定 token length / budget。
- 奖励主要依赖最终正确率，对中间步骤正确性没有精细监督。

### 9.2 是否依赖特定模型、数据集或人工标注？
- 依赖一个能服从长度约束的 solver（L1-Qwen3-8B-Exact）。
- 训练集中主要基于 MATH Level-5 分布，虽然有 OOD 评测，但跨领域泛化仍待更多验证。
- 不依赖人工逐步标注，但依赖可验证最终答案的任务。

### 9.3 是否存在泛化性、稳定性、成本、延迟、可解释性或部署方面的问题？
- RL 训练和多模型协作（User/Budgeter/Solver）带来系统复杂度。
- 如果未来 turn 不可预知，TAB All-SubQ 只能作为上界变体，真实交互式场景无法直接使用。
- 对非数学、不可验证奖励任务是否同样有效，尚未充分说明。

### 9.4 作者自己提到的 Limitation 是什么？
- 从当前提取到的前中段正文看，作者更强调多轮预算问题的重要性，明确 limitations 章节需要通读全文后补充；当前可确认的是论文没有完整展开 latency / serving 指标。

### 9.5 我认为还有哪些潜在问题？
- User LLM 先做题目分解这一设定会影响后续预算策略质量，若分解质量不好，预算再优也可能救不了最终结果。
- 预算只在固定离散桶 `{256, 512, 1024, 2048, 4096}` 中选，粒度仍较粗。
- 只控制 token 数，不控制“推理模式切换”“是否继续搜索”“是否换更强模型”，所以仍是单维 compute control。

## 10. 对我的启发
> 这一部分是把“读论文”变成“服务我自己的研究/工作”。

### 10.1 这篇论文对我理解大模型路由有什么帮助？
- 它提醒我：routing 不一定是“选模型”，也可以是“选每一步该花多少 compute”。
- 在 agent / decomposition 系统里，turn-level budget routing 很可能比 query-level model routing 更关键。

### 10.2 有哪些方法可以借鉴？
- 用 trajectory-level reward 学 budget policy，而不是只在单步上做 difficult/easy 分类。
- 将预算器与 solver 解耦，允许后续替换 solver 或把 budget control 插到任意多轮系统中。
- 用“已知未来子任务”的上界实验，来证明 planning information 的价值。

### 10.3 有哪些想法可以扩展？
- 把 TAB 扩展成 joint model-budget routing：同一 turn 同时选择模型和预算。
- 在 agent workflow 中，不只控制 token budget，还控制是否调用工具、是否并行、是否升级到更强 agent。
- 引入 response-level signal 做 post-turn 预算校正。

### 10.4 是否能用于以下场景？
- 企业内部 Copilot：适合，尤其是长流程问答和文档分析。
- LLM 系统路由：适合，可作为 budget control 子模块。
- 多模型选择：可扩展，但论文本身不直接做 model selection。
- 成本优化：非常适合。
- Agent 系统：很适合，尤其是 decomposition / planner-executor 系统。
