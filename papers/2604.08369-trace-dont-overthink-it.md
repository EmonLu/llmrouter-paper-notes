## 2. 一句话总结
> 用一句话说明：这篇论文解决了什么问题、用了什么方法、取得了什么结果。

- 总结：TrACE 用“多次 rollout 后下一步动作的一致性”作为无需训练的难度信号，在 agent 每个 timestep 自适应决定是否继续多采样，从而在 GSM8K 和 MiniHouse 上匹配 SC-4 / SC-8 的准确率，同时把 LLM 调用数减少 33%~65%。

## 3. 研究问题
> 这一部分回答“为什么要做这件事”。

### 3.1 核心问题是什么？
- 现有 inference-time compute scaling 常见做法是 greedy 或 fixed-budget self-consistency（每步固定采样 k 次）。
- 但 sequential agent 场景里，不同步骤的难度明显不同：有些动作非常显然，有些动作需要更多试探。
- 核心问题是：能否在不训练额外控制器、不依赖 verifier / labels 的前提下，在每个 step 自适应决定“要不要再想一会儿”？

### 3.2 为什么这个问题在大模型路由场景中重要？
- 这本质上是一个 training-free 的 per-step compute routing 问题：路由的不是模型，而是采样预算。
- 在 agent setting 中，统一给每一步同样采样次数会浪费大量调用，尤其是多步环境交互任务。
- 如果存在一个“免费”且可靠的难度信号，就能让 adaptive compute 真正在开源模型部署中落地。

### 3.3 该问题主要对应哪些目标？
> 可多选：质量、成本、延迟、可扩展性、鲁棒性、可解释性、在线适应性、部署效率等。

- 目标类型：成本、延迟、质量、部署效率
- 我的理解：TrACE 的重点不是提高绝对 SOTA，而是以尽可能少的额外机制，把 fixed-budget SC 变成更实用的 adaptive-compute controller。

## 4. 方法概览
> 这一部分回答“它是怎么做的”。

### 4.1 论文提出的方法是什么？
- 提出 TrACE（Trajectorical Adaptive Compute via agrEement）。
- 在每个 timestep：
  1. 先采样少量候选动作
  2. 计算这些动作的 plurality agreement
  3. 若 agreement 足够高，则立即提交该动作
  4. 否则继续增量采样，直到达到阈值或达到最大采样数
- 它不训练任何 router，不使用外部 verifier，也不需要人工标注。

### 4.2 Router 的输入是什么？
> 例如：query、历史对话、用户画像、候选模型特征、预算、延迟约束、环境状态等。

- 输入：
  - 当前 agent context `ct = (g, o1:t, a1:t-1)`
  - 初始若干个 stochastic rollout 的候选 next actions
  - 预设超参数：`kinit`, `kmax`, `τhigh`, sampling temperature

### 4.3 Router 的输出是什么？
> 例如：选择哪个模型、是否 fallback、是否 cascade、是否继续推理、分配多少预算等。

- 输出：
  - 当前 timestep 是否立即 commit
  - 若不 commit，是否继续追加 rollout
  - 最终提交的 plurality action
  - 隐含的 per-step LLM call budget（在 `kinit` 到 `kmax` 之间）

### 4.4 Routing 决策是如何产生的？
> 例如：规则、分类器、打分器、排序器、policy、bandit、gating network 等。

- 决策机制：基于 inter-rollout agreement 的 training-free rule。
- agreement 定义为：当前 plurality action 在所有 sampled actions 中所占比例 `αt`。
- 若 `αt >= τhigh` 则 commit；否则逐个加样本直到达到阈值或上限。

### 4.5 是否需要训练 Router？
- 是否训练：`否`
- 如果需要，训练数据是什么：无
- 训练目标是什么：无

### 4.6 涉及哪些学习机制？
> 可多选：强化学习、监督学习、蒸馏、bandit、ranking、classification、gating、heuristic 等。

- 学习机制：training-free heuristic / adaptive stopping
- 我的理解：TrACE 是“用行为一致性替代显式 confidence estimator”的一种轻量 compute controller。

## 5. 系统架构
> 这一部分回答“它在系统里怎么接入”。

### 5.1 整体 Pipeline 是怎样的？
- 对于每个 agent step：
  1. 先采样 `kinit` 个候选动作
  2. canonicalize 动作文本，算 plurality agreement
  3. agreement 高则直接提交
  4. agreement 低则继续 sample，到 `kmax` 为止
  5. 将 plurality action 执行到环境中，进入下一步

### 5.2 包含哪些模型 / 模块？
- 核心 LLM：Qwen 2.5 3B Instruct
- 控制器：TrACE（无参数）
- 基线：Greedy、SC-4、SC-8
- 环境：
  - GSM8K（single-shot reasoning）
  - MiniHouse（作者自建文本 household navigation 环境）

### 5.3 路由发生在哪个阶段？
> 例如：请求进入前、生成前、生成中、agent planning 阶段、tool 调用前后等。

- 路由阶段：每个 agent timestep 的 action proposal 阶段，即决定当前一步是否需要更多 rollout。

### 5.4 是否支持以下能力？
- 动态 fallback：`否`
- cascade：`部分像逐步扩展采样预算，但不是多模型 cascade`
- multi-step decision：`是`
- online update：`否`

### 5.5 我对系统架构的理解
- TrACE 可以看成一个“外挂在 agent action sampler 外面的 compute gate”。
- 它与 tree search、verifier-based reranking、PRM 并不冲突，理论上还能嵌入这些更复杂方法的节点展开阶段。

## 6. 实验设置
> 这一部分记录实验是否可信、是否和你的场景相关。

### 6.1 使用了哪些数据集？
- GSM8K：从 test split 中随机抽取 50 道题，用 single-shot 形式测试 agreement 信号是否能迁移到非 sequential 场景。
- MiniHouse：作者构建的轻量、无依赖、CPU-friendly 文本 household navigation 环境，共 30 个任务，3 个采样 seed。

### 6.2 对比了哪些 Baseline？

- SC-4：每步固定采样 4 次
- SC-8：每步固定采样 8 次
- TrACE-4：`kinit=2, kmax=4, τhigh=0.75`
- TrACE-8：`kinit=2, kmax=8, τhigh=0.75`

### 6.3 评估了哪些任务类型？
> 例如：chat、QA、math、code、tool-use、agent tasks、benchmark routing tasks 等。

- 数学推理（GSM8K，single-shot）
- 多步导航 / sequential decision（MiniHouse）

### 6.4 使用了哪些大模型或专家模型？
- Qwen 2.5 3B Instruct
- 量化格式：Q4_K_M（GGUF）
- 运行方式：llama-cpp-python
- 硬件：Apple M-series CPU，32GB RAM，8 threads
- 无 GPU

### 6.5 主要评估指标是什么？
> 例如：accuracy、win rate、cost、latency、token usage、throughput、success rate 等。

## 7. 核心结果
> 这一部分只记录最关键结果，不要机械抄整张表。

### 7.1 最重要的实验结果是什么？
- GSM8K：
  - Greedy：Acc 0.780，1.00 calls/task
  - SC-4：Acc 0.820，4.00 calls/task
  - SC-8：Acc 0.840，8.00 calls/task
  - TrACE-4：Acc 0.820，2.68 calls/task
  - TrACE-8：Acc 0.840，3.56 calls/task
- MiniHouse：
  - Greedy / SC-4 / SC-8 / TrACE-4 / TrACE-8 准确率都约 0.367
  - 但调用数显著不同：
    - Greedy：5.87
    - SC-4：24.67
    - SC-8：46.93
    - TrACE-4：15.07
    - TrACE-8：16.27

### 7.2 相比 Baseline 提升了什么？
- TrACE-4 在 GSM8K 上以 33% 更少 calls 匹配 SC-4 准确率；在 MiniHouse 上以 39% 更少 calls 匹配 SC-4。
- TrACE-8 在 GSM8K 上以 55% 更少 calls 匹配 SC-8；在 MiniHouse 上以 65% 更少 calls 匹配 SC-8。
- 论文强调其 Pareto-dominates fixed-budget self-consistency：同样准确率、更低调用数。

### 7.3 是否在质量、成本、延迟之间取得了更好的 trade-off？
- 是，而且非常直接：在不损失准确率时显著减少 LLM calls。
- MiniHouse 上 wall-clock 结果也支持这一点：
  - greedy 约 2.5 分钟
  - SC-8 约 40 分钟
  - TrACE-8 约 14 分钟
  - 即相对 SC-8 有约 65% 的 wall-clock 降低
- 但需要注意：在 MiniHouse 上所有方法准确率都卡在 0.367，说明这里更多展示的是效率优势，而非能力上限突破。

### 7.4 有哪些 Ablation Study 或 Sensitivity Analysis？
- `τhigh` 阈值敏感性：
  - `τhigh=1.00` 时接近 SC-kmax，需要接近一致才停止
  - `τhigh=0.50` 时过早停止，可能损失准确率
  - 默认 `τhigh=0.75` 位于 Pareto frontier 上
- agreement vs success 分析：在 MiniHouse 中，高 agreement step 更常出现在最终成功任务中，支持“agreement 是 step difficulty proxy”这一假设。
- 调用数分布分析：TrACE 呈现“easy step 停在 kinit，hard step 冲到 kmax”的双峰分布，这是 adaptive compute 的运行签名。

## 8. 贡献与创新点
> 这一部分用于提炼“这篇论文为什么值得记”。

### 8.1 主要贡献是什么？
- 提出第一个 training-free、per-timestep adaptive-compute controller，并显式在 sequential agent task 上评估。
- 证明 inter-rollout action agreement 可作为免费难度信号。
- 提供 MiniHouse 这种可 CPU 复现实验环境。

### 8.2 相比已有方法的新意在哪里？
- 相比 self-consistency：不是每步固定 k 次，而是按 agreement 动态决定预算。
- 相比 verifier / PRM / ORM：不需要任何训练和外部评分器。
- 相比 token-level uncertainty early stop：TrACE 用的是跨 rollout 的行为一致性，而不是单条生成流内部的不确定性。

### 8.3 创新类型属于哪一类？
> 可多选：新的 routing 策略、新的训练目标、新的数据构造方式、新的系统架构、新的 benchmark 等。

- 创新类型：新的 training-free compute routing 策略、新 benchmark（MiniHouse）
- 我的判断：这篇论文最大的亮点是“成本极低、概念简单、效果稳定”，很适合当作 adaptive compute 的轻量基线。

## 9. 局限性
> 这一部分非常重要，用来防止“只看到优点”。

### 9.1 方法有哪些假设？
- 假设动作空间可以 canonicalize，且不同 rollout 的“同一动作”能被识别出来。
- 假设高 agreement 与较高正确率正相关。
- 更适合 discrete / enumerated action space，而非开放式长文本生成。

### 9.2 是否依赖特定模型、数据集或人工标注？
- 不依赖训练数据或人工标注。
- 但当前只在单个 3B 模型和两个 benchmark 上评估。

### 9.3 是否存在泛化性、稳定性、成本、延迟、可解释性或部署方面的问题？
- 对 open-ended generation（长代码、网页操作、长计划文本）是否有效，文中明确说还不能保证。
- 如果 surface form 很发散，即使语义上动作相同，也可能被 agreement 低估。
- 在更强模型或 GPU serving 环境中，相对收益是否仍保持，尚未验证。

### 9.4 作者自己提到的 Limitation 是什么？
- 只用了单个 3B 模型和 CPU 环境，无法确认规模扩展性。
- GSM8K 只用 1 个 seed、50 个样本；MiniHouse 也只有 30 个任务 × 3 seeds。
- benchmark diversity 有限，尤其 MiniHouse 是作者自建的简单环境。
- 没与 trained methods（PRM、ORM、fine-tuned verifier）对比。
- `τhigh=0.75` 并未做系统性 sweep 到足够充分程度。

### 9.5 我认为还有哪些潜在问题？
- 如果 agent 行为空间巨大，plurality action 本身可能不稳定，agreement 作为难度指标会变弱。
- 该方法更适合“采样式决策器”，不一定适配 deterministic constrained decoding 流程。
- 准确率不提升时，TrACE 的价值主要是省调用；对追求最终任务质量极限的系统，它可能只是配角而非核心解法。

## 10. 对我的启发
> 这一部分是把“读论文”变成“服务我自己的研究/工作”。

### 10.1 这篇论文对我理解大模型路由有什么帮助？
- 它说明“免费信号”也可以做 compute routing，不一定非要训练一个 difficulty estimator。
- 在 agent 场景下，step-level uncertainty 比 query-level difficulty 更贴近真实资源分配问题。

### 10.2 有哪些方法可以借鉴？
- 先小样本 probing，再按 agreement 决定是否追加采样。
- 用行为一致性而不是 verbalized confidence 作为 routing signal。
- 在多步系统里，把 compute routing 设计成外插控制层，而不是侵入式改动主模型。

### 10.3 有哪些想法可以扩展？
- 把 agreement signal 接到 tree search 节点扩展上，决定哪些节点值得继续搜索。
- 结合 model routing：agreement 低时不仅追加采样，还可升级到更强模型。
- 在 tool-use / web agent 中引入 action clustering，缓解 surface form 发散问题。

### 10.4 是否能用于以下场景？
- 企业内部 Copilot：适合短动作、多步流程的 agent。
- LLM 系统路由：适合当 compute gate。
- 多模型选择：可扩展，但文中本身不做 model routing。
- 成本优化：非常适合。
- Agent 系统：高度相关。
