## 2. 一句话总结
> 用一句话说明：这篇论文解决了什么问题、用了什么方法、取得了什么结果。

- 总结：GraphPlanner 把多模型路由从“选一个模型”推进到“生成一条多智能体工作流”，通过异构图记忆 GARNet 联合编码历史交互和当前 workflow，用 PPO 学习在每一步同时选择 agent role 与 LLM backbone，在 14 个任务上相对强单轮/多轮 router 取得最高 +9.3% 的准确率提升，并把训练 GPU 计算量降到 1.04 GiB 级别。

## 3. 研究问题
> 这一部分回答“为什么要做这件事”。

### 3.1 核心问题是什么？
- 现有 router 大多还停留在 single-round 或 multi-round model selection：要么一次性选模型，要么根据上下文多轮选模型。
- 但复杂任务往往需要多 agent 协作、任务分解、角色分工和历史记忆利用；仅仅“每次选个模型”不足以表达 agentic workflow。
- 核心问题因此变成：如何让 router 直接生成多智能体协作 workflow，并在流程中联合决定“谁做什么、用哪个模型做”。

### 3.2 为什么这个问题在大模型路由场景中重要？
- 当 routing 进入 agent setting，决策对象不再只是 backbone model，而是 `agent role × model` 的组合。
- 早期错误决策会影响后续整个工作流，属于典型 delayed reward 场景。
- 历史成功/失败轨迹本来蕴含大量关于协作模式的信息，但传统 router 很少系统化利用这些 memory。

### 3.3 该问题主要对应哪些目标？
> 可多选：质量、成本、延迟、可扩展性、鲁棒性、可解释性、在线适应性、部署效率等。

- 目标类型：质量、成本、可扩展性、泛化性、部署效率
- 我的理解：GraphPlanner 的目标不是“让每一步更聪明”而已，而是让整条协作路径更适合当前 query，同时保持更好的 cost-performance trade-off。

## 4. 方法概览
> 这一部分回答“它是怎么做的”。

### 4.1 论文提出的方法是什么？
- 提出 GraphPlanner，一个 heterogeneous graph memory-augmented agentic router。
- 它把 agentic workflow generation 建模为 MDP 中的 graph generation 过程。
- 每一步 action 同时选择：
  - agent role（Planner / Executor / Summarizer）
  - 对应的 LLM backbone
- 通过 GARNet（Graph-based Agentic Routing Network）联合整合：
  - 当前 workflow graph `Gworkflow`
  - 历史记忆 graph `Ghistory`
- 最终用 PPO 优化路由策略，使最终答案性能与计算成本共同受益。

### 4.2 Router 的输入是什么？
> 例如：query、历史对话、用户画像、候选模型特征、预算、延迟约束、环境状态等。

- 输入：
  - 当前 query 或当前 sub-query
  - 当前 workflow memory graph
  - 历史 interaction memory graph
  - 候选 agent roles
  - 候选 LLM backbones 及其隐含性能/成本特征

### 4.3 Router 的输出是什么？
> 例如：选择哪个模型、是否 fallback、是否 cascade、是否继续推理、分配多少预算等。

- 输出：
  - 当前 step 选择的 `(agent role, LLM backbone)` 二元组
  - 逐步扩展得到的完整 multi-agent workflow graph

### 4.4 Routing 决策是如何产生的？
> 例如：规则、分类器、打分器、排序器、policy、bandit、gating network 等。

- 决策机制：
  - 把 workflow 生成视作 sequential decision process
  - 用 GARNet 编码状态表示
  - 用 PPO 学习 policy
  - reward 同时考虑 task-specific utility 与 computational cost，文中给出 `U(y_hat, y*) - α C(a_t)` 风格目标

### 4.5 是否需要训练 Router？
- 是否训练：`是`
- 如果需要，训练数据是什么：14 个任务、6 个领域上的 agentic routing 训练数据与历史交互轨迹，具体切分见 appendix
- 训练目标是什么：在多任务场景中学习能兼顾正确率与成本的 workflow generation policy

### 4.6 涉及哪些学习机制？
> 可多选：强化学习、监督学习、蒸馏、bandit、ranking、classification、gating、heuristic 等。

- 学习机制：强化学习（PPO）、异构图表示学习、记忆增强建模
- 我的理解：GraphPlanner 的关键不是“GNN router”本身，而是“把 routing object 从单步选模扩展到 agent workflow graph”。

## 5. 系统架构
> 这一部分回答“它在系统里怎么接入”。

### 5.1 整体 Pipeline 是怎样的？
- 给定 query，GraphPlanner 不直接输出一个模型，而是逐步生成 workflow。
- 在每个 step：
  1. 读取当前 query / sub-query 与当前 workflow state
  2. 结合历史交互记忆和当前图状态，经 GARNet 编码
  3. 选择下一步的 agent role 和 backbone
  4. 产生新的中间 response，并把节点/边加入 graph
- 最终由 Summarizer 角色整合中间结果得到 final answer。

### 5.2 包含哪些模型 / 模块？
- Agent roles：Planner、Executor、Summarizer
- Router：GraphPlanner policy
- Graph memory encoder：GARNet
- Memory structures：
  - `Gworkflow`：当前 episode 内部的工作流图
  - `Ghistory`：跨 episode 的历史交互图
- RL optimizer：PPO

### 5.3 路由发生在哪个阶段？
> 例如：请求进入前、生成前、生成中、agent planning 阶段、tool 调用前后等。

- 路由阶段：agent planning / workflow generation 阶段，并在整个多步推理过程中持续发生。

### 5.4 是否支持以下能力？
- 动态 fallback：`部分是，本质上可通过 workflow 继续扩展或切换角色/模型`
- cascade：`可视作更一般的多阶段 agentic routing`
- multi-step decision：`是`
- online update：`论文主设定是离线训练；推理时支持 inductive / transductive memory use，但不是典型在线学习`

### 5.5 我对系统架构的理解
- 这篇论文把 router 升级成了“workflow planner”。
- 相比 Router-R1 这类 multi-round router，GraphPlanner 更强调结构化协作图，而不仅是顺序调用序列。
- GARNet 的价值在于把历史交互经验和当前流程状态放在同一图语义空间中，让策略有“经验记忆”。

## 6. 实验设置
> 这一部分记录实验是否可信、是否和你的场景相关。

### 6.1 使用了哪些数据集？
- 共 14 个任务、6 个领域。
- In-domain 任务包括：
  - Math：GSM8K、MATH
  - Code：MBPP、HumanEval
  - Commonsense Reasoning：CommonsenseQA、ARC、OpenBookQA
  - World Knowledge：NaturalQuestions、TriviaQA
  - Popular：MMLU、GPQA
- Out-of-domain / unseen datasets：
  - LogicGrid
  - MGSM
  - CommonGen

  - 训练 / 测试数一般为 `500/50`；MATH 也是 `500/50`
  - MBPP 为 `374/50`，HumanEval 为 `120/44`
  - GPQA 为 `400/44`
  - LogicGrid、MGSM、CommonGen 不参与训练，仅各有 50 个测试样本
- appendix 表 9 还列明指标：数学与大多数 QA 任务用 Accuracy，MBPP / HumanEval 用 Pass@1，NaturalQuestions / TriviaQA 用 CEM，CommonGen 用 Coverage。

### 6.2 对比了哪些 Baseline？
- Single-round routers：
  - RouterKNN
  - RouterMLP
  - RouterSVM
  - RouterDC
  - GraphRouter
- Multi-round routers：
  - Prompt LLM
  - Router-KNN-MR
  - R2-Reasoner
  - Router-R1

### 6.3 评估了哪些任务类型？
> 例如：chat、QA、math、code、tool-use、agent tasks、benchmark routing tasks 等。

- 数学推理
- 代码生成
- 常识推理
- 世界知识问答
- 通用考试/学术 benchmark
- 零样本未见任务泛化

### 6.4 使用了哪些大模型或专家模型？

- small scale：Qwen2.5-7B、CodeGemma-7B、Mistral-7B、LLaMA-3.1-8B、LLaMA-3 ChatQA-8B、Gemma-2-9B 等。

### 6.5 主要评估指标是什么？
> 例如：accuracy、win rate、cost、latency、token usage、throughput、success rate 等。

- 训练期的 token usage、GPU compute、average LLM calls
- Pareto frontier 上的性能-成本折中

## 7. 核心结果
> 这一部分只记录最关键结果，不要机械抄整张表。

### 7.1 最重要的实验结果是什么？
- 在两阶段评测中，GraphPlanner 持续优于单轮与多轮 router：
  - Phase 1 平均准确率至少比最强 baseline 高 `+3.8%`
  - Phase 2 平均准确率至少比最强 baseline 高 `+9.3%`
- 训练成本方面，GraphPlanner 把 GPU compute 从 `186.26 GiB` 级别降到 `1.04 GiB`，同时维持 Pareto frontier 优势。
- 在未见任务上，GraphPlanner 零样本平均准确率达到 `78%`，显著高于 GraphRouter 的 `46%`、RouterDC 的 `58%` 和 Router-R1 的 `38%`。
- 未见任务细项上：
  - LogicGrid：60%
  - MGSM：92%
  - CommonGen：82%
- appendix 表 4 还给出训练期代价对比：GraphPlanner 使用 `182.45k` training tokens / `1.04 GiB` GPU compute / `4.25` 平均训练 LLM calls；Router-R1 则是 `150.36k` / `186.26 GiB` / `1.18`。这说明它不是通过更少交互取胜，而是用更轻的 policy 训练把 GPU 开销压了下来。

### 7.2 相比 Baseline 提升了什么？
- 相比 single-round routers：不再局限于 query-level one-shot assignment，而是能为复杂 query 生成更适合的协作 workflow。
- 相比 multi-round routers：显式建模 agent role 与合作结构，减少“只是多轮调用，但不形成协作图”的局限。
- 在 reasoning-heavy 场景（Math、Code）收益尤其明显，文中指出这两类任务分别可带来约 `5.0%` 与 `4.0%` 的增益。

### 7.3 是否在质量、成本、延迟之间取得了更好的 trade-off？
- 是。论文明确指出 GraphPlanner 在 Figure 4 上形成 Pareto frontier，可通过调节 cost-utility 系数 `α` 在高精度和低成本间灵活切换。
- 它不仅准确率更高，而且训练期 token / GPU 开销更低，说明不是单纯“砸更多算力换更高分”。
- 推理期文中主要强调成本而非 wall-clock latency；但 inductive / transductive 两种模式提供了部署层面的效率-效果可切换空间。

### 7.4 有哪些 Ablation Study 或 Sensitivity Analysis？
- Historical memory ablation：
  - `w/o History`
  - `Homo-Graph`
  - `Hetero-Graph`
  - Full `GARNet`
- 结果显示去掉历史记忆会显著掉点，说明 accumulated interactions 确实有用。
- Inferencing mode ablation：
  - Inductive：不在推理时保留/复用训练历史，较轻量
  - Transductive：推理时使用保留历史，准确率略高但成本更高
- Unseen tasks / unseen LLMs generalization：验证模型对新领域与新模型池的鲁棒性。
- appendix 还补全了复现实验超参：PPO 使用 `γ=0.99`、`ϵ=0.2`、每次更新 `k=4` epochs；hidden dim 32，candidate embedding dim 1536，state embedding dim 768；policy learning rate `3e-4`、value network learning rate 翻倍；梯度裁剪 0.5，BF16 + gradient checkpointing；最多训练 1000 episodes，单卡 NVIDIA A6000。

## 8. 贡献与创新点
> 这一部分用于提炼“这篇论文为什么值得记”。

### 8.1 主要贡献是什么？
- 首次较系统地把 LLM routing 推进到 agentic workflow generation 视角。
- 提出 GARNet，把历史记忆与当前工作流记忆统一到异构图里。
- 用 PPO 训练 role-model joint routing policy。
- 在多任务、未见任务、未见 LLM 上都展示了较强泛化能力。

### 8.2 相比已有方法的新意在哪里？
- 单轮 router 只选模型；GraphPlanner 选的是“角色 + 模型 + 工作流扩展”。
- 多轮 router 虽会重复调用模型，但未必显式建模协作关系；GraphPlanner 用图结构把协作关系显性化。
- 历史记忆不是简单存日志，而是作为异构图节点/边真正参与推理状态表示。

### 8.3 创新类型属于哪一类？
> 可多选：新的 routing 策略、新的训练目标、新的数据构造方式、新的系统架构、新的 benchmark 等。

- 创新类型：新的 agentic routing 策略、新的系统架构、图记忆建模、RL 训练范式
- 我的判断：这篇论文是“从 model router 走向 workflow router”的典型代表作。

## 9. 局限性
> 这一部分非常重要，用来防止“只看到优点”。

### 9.1 方法有哪些假设？
- 假设任务适合用 Planner / Executor / Summarizer 这三类角色刻画。
- 假设历史 interaction memory 足够有价值，且能被图结构有效利用。
- 假设 workflow generation 的 RL 训练成本是可接受的。

### 9.2 是否依赖特定模型、数据集或人工标注？
- 依赖一个较大的候选 LLM pool 和对应任务切分。
- 依赖图结构化历史轨迹的构造方式。
- 不依赖人工 step-level 标注，但需要任务级 utility 和 cost 定义。

### 9.3 是否存在泛化性、稳定性、成本、延迟、可解释性或部署方面的问题？
- 虽然结果显示有较强泛化，但 workflow 级 RL router 仍然比普通 classifier router 更复杂，更难线上部署。
- transductive 模式效果更好但要维护历史记忆，带来额外存储和查询开销。
- 角色集合目前较固定，未来遇到更复杂 agent 生态时，手工定义的 role space 可能不足。

### 9.4 作者自己提到的 Limitation 是什么？
- 论文结尾明确提到未来会纳入比 Planner / Executor / Summarizer 更丰富的 agent profile，暗示当前角色集合仍偏简化。

### 9.5 我认为还有哪些潜在问题？
- 论文更强调任务表现和成本，对在线服务 latency、容错、缓存命中等系统指标讨论较少。
- 如果历史 memory 分布偏移明显，GARNet 可能把旧经验带入新任务，存在 memory bias 风险。
- 作为统一 router，在 14 任务跨域训练上的效果很好，但迁移到企业私有 agent workflow 时仍需验证。

## 10. 对我的启发
> 这一部分是把“读论文”变成“服务我自己的研究/工作”。

### 10.1 这篇论文对我理解大模型路由有什么帮助？
- 它让我更清楚地看到：agentic routing 不再只是“选模型”，而是“选 workflow topology”。
- 对我做多智能体系统时，router 也许应该输出一个图，而不是单个 action。

### 10.2 有哪些方法可以借鉴？
- 用 role × model 的联合动作空间替代单一模型选择。
- 把历史 interaction 结构化成图记忆，而不是只拼接成长文本上下文。
- 在部署上同时准备 inductive / transductive 两种模式，对应不同资源预算。

### 10.3 有哪些想法可以扩展？
- 加入 tool selection、budget allocation、memory retrieval 深度，形成更完整的 workflow router。
- 把 GraphPlanner 和 TAB 类方法结合，在 workflow 生成的同时控制每个节点的 compute budget。
- 探索 role space 自动发现，而不是固定三类角色。

### 10.4 是否能用于以下场景？
- 企业内部 Copilot：适合复杂任务编排场景。
- LLM 系统路由：非常适合，是从 model router 升级到 workflow router 的思路。
- 多模型选择：适合，但前提是你需要多 agent 协作而不是单次问答。
- 成本优化：适合，尤其是需要在不同模型池间组合协作时。
- Agent 系统：高度相关。
