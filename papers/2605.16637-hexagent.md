## 2. 一句话总结
- 总结：HexAGenT 把 agentic LLM serving 从“独立请求排队”改成“在线揭示 DAG 的工作流调度”问题，用 workflow horizon + projected-risk ranking + joint prefill/decode placement + async plan application 来优化端到端 workflow SLO，在异构 A100/H100/H200 的 P-D serving 集群上，把满足 95%/99% workflow attainment 所需的 SLO scale 平均分别压低 20.1%/33.0%，说明 agent 时代的 serving 调度目标必须从 call latency 升级为 workflow completion。

## 3. 这篇论文到底在解决什么问题？
### 3.1 核心问题是什么？
- 真实 agent 请求不是一次独立 LLM 调用，而是多步 workflow：规划、工具调用、分支、反思、合成。
- 用户真正感知的是整个 workflow 的完成时间，而不是单次 call 的 latency。
- 现有 serving system 大多仍按“单个请求 / 单个 call”做排队和 placement，因此会优化错目标：局部 call 变快，不等于整条 workflow 更快完成。

### 3.2 为什么这个问题在 agent 系统里重要？
- agentic workload 有三类典型难点同时出现：
  - DAG 在线揭示：后续节点要等前面节点和工具返回后才出现
  - 负载异质：不同 call 的 prompt 长度、输出长度、KV-cache 需求差异很大
  - 硬件异质：A100/H100/H200 在 prefill / decode / transfer 上表现不同
- 这意味着 agent serving 的核心调度目标必须从“谁先排队”升级为“如何尽快让整条 workflow 在目标 SLO 内完成”。

### 3.3 它主要在优化什么目标？
- 目标类型：端到端延迟、workflow-level SLO attainment、异构资源利用率、tail latency、部署经济性
- 我的理解：这篇论文本质上是在做 agent runtime 的 serving control plane，而不是单纯的 GPU 负载均衡。

### 3.4 它的控制对象到底是什么？
- 控制对象：
  - workflow 内 ready call 的调度顺序
  - prefill placement
  - decode placement
  - local queue priority
- 控制粒度：call-level action，但优化目标是 workflow-level
- 我对其定位的判断：这是 agentic serving scheduler / workflow-aware runtime controller，不是 model router。

### 3.5 它更像哪一类工作？
- `agent runtime architecture`
- `workflow controller`
- `budget / latency controller`
- `observability / scheduling framework`
- 我的判断：最像 serving-oriented workflow controller，补的是“agent runtime 在系统层如何调度”的一块空白。

## 4. Agent Loop / Runtime Mechanism
### 4.1 它提出的核心机制是什么？
- HexAGenT 把每个 agentic request 抽象成一个 online-revealed DAG。
- 对每个 workflow，它维护一个当前的 standalone completion horizon `H_w(t)`，作为这条 workflow 当前应达到的端到端目标。
- 对每个 ready call，它估计若现在调度该 call，会给 workflow 的 scaled-SLO 带来多大风险，然后按风险排序。
- 调度时不是只决定“先跑谁”，而是联合决定：
  - 哪个 prefill instance 跑它
  - 哪个 decode instance 接它
  - 它在本地 queue 里的优先级

### 4.1.1 核心直觉是什么？
- 对 agent serving 来说，最重要的不是每个 call 尽快结束，而是关键路径上的 workflow 不要被拖垮。
- 同一个 call 放在不同 prefill/decode 组合上，端到端影响差异很大，尤其在异构 GPU 和有 KV-transfer 的 P-D deployment 里更明显。
- 所以 scheduler 既要知道“哪条 workflow 更急”，也要知道“哪组 prefill/decode 放置最能降低这条 workflow 的风险”。

### 4.1.2 整个 agent loop / scheduling loop 按步骤是怎么运行的？
- Step 1：workflow front-end 接收用户请求，只暴露 source calls，把 workflow 初始化为 online-revealed DAG。
- Step 2：State Collector 收集跨阶段运行态：prefill queues、decode queues、running calls、KV usage、带宽与 workflow progress。
- Step 3：Estimator 用 roofline-style model 估计候选 placement 下的 prefill、decode、transfer 与 KV 需求。
- Step 4：为每个 workflow 更新在线 horizon `H_w(t)`，表示当前已揭示子图若独占同一集群时的完成时间。
- Step 5：对当前 waiting calls，计算 projected ratio `R_s(c,t)=((t-a_w)+Δ_s(c,t))/H_w(t)`；ratio 越大，说明越接近或越超过该 workflow 当前目标。
- Step 6：Greedy planner 优先挑最紧急的 call，并为其选择最优 prefill/decode pair 与本地 queue priority。
- Step 7：Plan Dispatcher 异步下发 scheduling plan；如果 call 已开始服务，则迟到计划不会强行改写运行事实。
- Step 8：随着 prefill completion、transfer completion、decode completion 发生，新节点被揭示，再次进入下一轮 event-driven scheduling。

### 4.1.3 如果把它压缩成一个决策流 / 伪代码，它长什么样？
- `on event -> update runtime state -> update workflow horizons -> collect waiting calls -> for each call estimate best feasible P/D placement -> compute projected risk ratio -> greedily assign most urgent call -> asynchronously apply plan to still-waiting calls`
- 它的关键不是复杂学习 policy，而是“workflow horizon + projected risk + joint placement”的组合。

### 4.2 runtime 的输入 state 是什么？
- workflow arrival time
- 当前已揭示 DAG 子图 `G_w(t)`
- runnable frontier
- prefill queues / decode queues
- running calls
- decode KV capacity
- cross-stage transfer bandwidth / latency
- 每个 call 的 input length、predicted output length
- 当前 workflow progress 与 horizon `H_w(t)`

### 4.3 runtime 的输出 action 是什么？
- 选哪个 prefill instance
- 选哪个 decode instance
- 设定 call 在各 stage 的 local queue priority
- 在 decode stage 是否允许 admission（受 KV capacity 约束）

### 4.4 决策是怎么产生的？
- 决策机制：规则化的 projected-risk ranking + heterogeneity-aware greedy planning
- 是否训练：`否`
- 如果训练，训练数据是什么：无
- 训练目标是什么：无
- 我的理解：这是一套系统调度算法，不是 learned router。

### 4.5 这个控制回路是单步的还是跨轨迹持续更新的？
- 控制范围：单条 workflow 内多步控制，同时跨 workflow 做全局资源竞争调度
- 我的理解：它在每个运行时事件点重算局部最优，因此是 event-driven、跨轨迹持续更新的调度闭环。

### 4.6 这套机制最依赖哪些关键信号？
- workflow horizon `H_w(t)`
- projected elapsed time `Δ_s(c,t)`
- projected ratio `R_s(c,t)`
- prefill / decode 异构服务时间估计
- KV-cache capacity feasibility
- cross-stage transfer latency

### 4.7 这套机制最容易失败在哪一步？
- 如果 serving latency 估计误差太大，可能选错 prefill/decode pair。
- 如果 workflow horizon 更新不准，会误判哪条 workflow 更急。
- 如果 async scheduling 太慢，更多 call 会在 fallback plan 下启动，削弱收益。
- 如果 decode KV-capacity 建模不准，会在尾部 workload 上产生 admission 偏差。

## 5. Context / State / Memory Management
### 5.1 系统如何表示当前状态？
- 状态表示：workflow DAG + live queue state + running-call state + KV state + transfer state + workflow progress state
- 是否结构化：`是`
- 我对这种表示的理解：这不是 message history 级 memory，而是面向 serving scheduler 的结构化 runtime state。

### 5.2 Context 是如何组织的？
- 上下文组织方式：以 workflow DAG 和 serving-stage state 为主，不关心语义文本内容本身，而关心长度、依赖和资源需求
- 上下文来源：前端工作流状态、队列状态、服务时延估计、带宽与容量快照
- 对成本 / 质量的影响：它不直接改模型质量，但直接影响 workflow 何时完成，从而影响 agent 系统端到端可用性

### 5.3 是否讨论了 context compaction / summarization / truncation？
- 是否支持：`否，非论文重点`

### 5.4 是否有 memory 机制？

- 读写时机：每次调度事件发生时读；每次服务状态变化后写
- 写入内容：queue state、KV state、workflow progress、完成反馈
- 检索方式：调度器直接读取系统态
- 我对其价值的判断：这是 serving scheduler 所必需的状态记忆，而不是 agent 语义 memory。

- 对 recovery 的意义：更多是服务内态追踪，而不是用户级 session persistence

### 5.6 如果上下文爆掉、会话中断或执行被打断，系统怎么恢复？
- 论文重点不在 agent 会话恢复，而在 runtime scheduling continuity。
- 其核心恢复思路是：通过 event-driven rescheduling 和 async plan application 保持服务前台继续推进，避免调度过程阻塞执行路径。

## 6. Tool Use / Environment Interaction
### 6.1 系统能调用哪些工具 / 环境？
- 论文不重新定义 tool API。
- 它服务的是包含 tool use 的 agentic workflows，实验里覆盖 BFCL-v3 function-calling、LATS tree-search、ShareGPT chain 等工作负载。

### 6.2 工具调用的语义是什么？
- 工具是 workflow DAG 中让后续节点被揭示的外部事件之一。
- scheduler 不决定工具语义，只处理“工具返回后新节点何时进入调度”。

### 6.3 环境交互发生在哪一层？
- 在 workflow front-end 和 external services 层。
- HexAGenT 自己负责的是 scheduling control，而不是 agent planning 语义层。

## 7. 系统架构
### 7.1 整体 Pipeline
- Workflow Front-End：接收请求，维护 online DAG reveal
- Global Scheduler：
  - State Collector
  - Estimator
  - Joint Planner
  - Plan Dispatcher
- Disaggregated P-D Serving Cluster：prefill pool + decode pool
- External Services：LLM weights / tools

### 7.2 包含哪些模型 / 模块？
- 调度模块：HexAGenT scheduler
- serving substrate：SGLang v0.5.9 的 P-D disaggregated serving
- estimator：roofline-style latency model
- simulator：约 4.6K 行 Python，模拟 waiting prefill / prefill / KV transfer / waiting decode / decode / completion 全流程

### 7.3 路由 / 调度发生在哪个阶段？
- 发生在 serving runtime，而不是模型推理前的 query-level model routing。
- 更具体地说：
  - workflow arrival
  - newly revealed prefill work
  - transfer completion into decode
  这几类事件会触发新的 scheduling。

### 7.4 是否支持 fallback / cascade / online update？
- fallback：支持。当 planner in flight 时，尚未被分配的 calls 可暂时按 safe fallback policy 走。
- online update：支持。每次事件发生都会更新状态并重算调度。
- cascade：不是模型 cascade，而是 P-D 多阶段调度。

### 7.5 我的理解
- 这篇论文真正解决的是“agent 时代的 serving 目标函数错位”问题。
- 它说明你不能再把 agent workload 当成一堆独立 LLM requests 来排队；workflow 本身必须成为一等调度对象。

## 8. 实验设置
### 8.1 使用了哪些数据集 / 工作负载？
- ShareGPT：100 个 conversational-chain workflows，10 workflows/s
- BFCL-v3：400 个 function-calling workflows，40 workflows/s
- LATS：100 个 tree/search-style workflows，40 workflows/s
- Mixed：混合 ShareGPT、BFCL-v3、LATS，100 workflows，10 workflows/s

### 8.2 对比了哪些 Baseline？
- SGLang-FCFS：per-call FCFS
- SGLang-LLF：workflow-level least-laxity-first
- Autellix-ATLAS：program-aware attained-service baseline
- 另外在 characterization 里还显式比较了 Workflow-FCFS

### 8.3 评估了哪些任务类型？
- conversational chains
- function-calling workflows
- tree/search workflows
- mixed agentic workloads

### 8.4 使用了哪些大模型或系统配置？
- 模型：
  - Llama 3.1-70B
  - Qwen 3-235B-A22B
- 异构集群：A100 / H100 / H200
- Hetero-1：8 prefill + 8 decode，每个池 2 A100 + 3 H100 + 3 H200
- Hetero-2：10 prefill + 10 decode，每个池 3 A100 + 4 H100 + 3 H200
- 同构集群：
  - Llama 用 H200 4P+4D
  - Qwen 用 A100 4P+4D

### 8.5 主要评估指标是什么？
- Req95：达到 95% workflow SLO attainment 所需最小 scale factor
- Req99：达到 99% workflow SLO attainment 所需最小 scale factor
- Scheduler overhead：总调度时间、每次调用毫秒数
- 评估原则：越低越好

## 9. 核心结果
### 9.1 最重要的实验结果是什么？
- 摘要 headline：在 representative agentic workloads 和 heterogeneous A100/H100/H200 集群上，HexAGenT 将 95%/99% attainment 所需 SLO scale 平均分别降低 20.1% / 33.0%，最大可到 45.0% / 80.5%。
- 在主异构评测表里，相对 strongest baseline 的平均改进为：
  - Req95 平均下降 13.0%
  - Req99 平均下降 24.5%
- Qwen Hetero-1 上平均表现最突出：
  - 从 5.60 / 7.22 降到 4.48 / 4.69
  - 对应 21.1% / 33.1% 改进

### 9.2 相比 Baseline 提升了什么？
- Characterization 阶段：
  - Workflow-FCFS 相比 per-call FCFS，Req95 平均下降 31.4%，Req99 平均下降 23.3%
  - HexAGenT 再相对 Workflow-FCFS，Req95 平均下降 26.9%，Req99 平均下降 42.6%
- Qwen Hetero-1 细分 workload：
  - ShareGPT：3.36 / 3.50 vs 4.58 / 5.45，下降 26.7% / 35.9%
  - BFCL-v3：8.39 / 8.57 vs 8.90 / 11.13，下降 5.7% / 23.0%
  - LATS：2.71 / 2.74 vs 3.06 / 3.33，下降 11.3% / 17.7%
  - Mixed：3.48 / 3.94 vs 5.85 / 8.96，下降 40.6% / 56.0%
- 说明 Mixed 和 ShareGPT 这类关键路径明显、队列压力不均的工作负载最吃 workflow-aware placement 的收益。

### 9.3 trade-off 如何？
- HexAGenT 不是免费午餐：它付出的是更多 CPU 侧规划开销。
- 但这个代价相对小：
  - Llama Hetero-1：10.2 ms / invocation
  - Llama Hetero-2：7.1 ms / invocation
  - Qwen Hetero-1：14.7 ms / invocation
  - Qwen Hetero-2：11.5 ms / invocation
  - 最坏平均值约 23.7 ms
- 作者结论是：几毫秒到十几毫秒的规划开销，换来明显更小的 workflow tail SLO scale，是值得的。

### 9.4 Ablation / Robustness / Appendix 关键补充
- 同构集群上依然有效：
  - Llama H200 4P+4D：Req95/Req99 下降 24.8% / 36.8%
  - Qwen A100 4P+4D：Req95/Req99 下降 23.1% / 33.9%
- 说明它不只依赖硬件异构，workflow-aware ordering 本身就有效。
- 对估计误差也较稳：
  - Llama 在 30% 估计误差下，Req99 平均退化仍在 1.5% 内
  - Qwen 更敏感，但退化仍然受限，说明方法不需要非常精确的 latency predictor 才有用

## 10. 贡献与创新点
### 10.1 主要贡献
- 把 agentic serving 抽象成 online-revealed DAG scheduling 问题
- 提出 workflow horizon `H_w(t)` 作为动态 serving target
- 提出 projected-risk ratio 做 workflow-aware urgency ranking
- 联合优化 prefill placement、decode placement、queue priority
- 将 async plan application 融进 P-D disaggregated serving runtime

### 10.2 相比已有方法的新意
- 相比 FCFS / queue-length 类方法：它直接对 workflow-level objective 优化，而不是 call-level queue latency。
- 相比 workflow-aware baseline（如 Workflow-LLF、ATLAS）：它进一步把异构 prefill/decode placement 和 KV transfer latency 联合进来。
- 相比一般 program-aware serving：它更贴近 agent 在线揭示 DAG 和 P-D disaggregation 的组合场景。

### 10.3 创新类型
- scheduling objective 创新
- runtime abstraction 创新
- system algorithm 创新
- agentic serving benchmark / evaluation protocol 补充

## 11. 局限性
### 11.1 方法假设
- 依赖对 prefill/decode latency、transfer latency、output length 的估计。
- 假设 workflow 可以被在线揭示成 DAG。
- 假设 P-D disaggregated serving 是底层部署架构。

### 11.2 依赖特定模型 / 数据 / 标注吗？
- 不依赖标注数据或训练集。
- 但依赖 SGLang P-D serving、roofline-style estimator、异构 GPU 部署假设。

### 11.3 泛化、稳定性、成本、部署问题
- 目前主要在 ShareGPT/BFCL/LATS/Mixed 这类代表性 trace 上评测，还不是覆盖所有 agent product 的真实 workload。
- 需要工程侧拿到较细的 runtime state，接入门槛高于普通排队策略。
- 如果部署环境不是 P-D disaggregation，部分收益来源会减弱。

### 11.4 作者自己提到的 limitation
- 论文没有宣称解决所有 agent serving 问题，重点是 workflow-aware + heterogeneity-aware scheduling。
- 调度器仍然依赖 latency estimation；虽然实验证明有鲁棒性，但不代表估计误差可以无限大。

### 11.5 我认为的潜在问题
- 这篇论文更像 infrastructure paper，不直接回答“agent 如何做更好推理”，因此和上层 routing / planning 的接口还需要你自己再设计。
- 它目前优化的是 latency/SLO，而不是 cost-quality frontier；若未来同时要联动模型选择和 serving placement，还需要上层 router + 下层 scheduler 联合设计。

## 12. 对我的启发
### 12.1 对 agentic router 的帮助
- 如果你未来做 Coding Agentic Router，不能只想“哪一步用哪个模型”，还要想“这一步应该在哪种系统资源上跑、以什么优先级跑”。
- 这篇论文说明 agent runtime 的 control plane 至少分两层：
  1. 语义层：选模型 / 预算 / workflow mode
  2. 系统层：placement / queue / resource scheduling

### 12.2 可借鉴的方法部件
- online-revealed DAG abstraction
- workflow horizon 作为动态目标
- projected-risk urgency score
- joint prefill/decode placement
- async plan application

### 12.3 可扩展想法
- 你可以把 future coding-agent router 设计成“双层路由器”：
  - 上层做 step-level model / budget routing
  - 下层借鉴 HexAGenT 做 runtime scheduling
- 对 SWE-bench agent 来说，还可以进一步把 `step importance`、`patch verification pressure`、`tool wait time` 纳入 horizon 更新逻辑。

### 12.4 适用场景
- 多步 agent workflow serving
- P-D disaggregated LLM serving
- heterogeneous GPU cluster
- 对 workflow tail latency 敏感的在线 agent 产品

- 先在单机 / 仿真环境里复现它的 event-driven simulator 和 projected-risk scheduler。
- 然后再把 scheduler 挂到现有的 P-D serving stack 上，先跑 Qwen Hetero-1 或简化版 BFCL / Mixed trace。
